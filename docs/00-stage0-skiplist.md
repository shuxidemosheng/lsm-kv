# 阶段 0：跳表 MemTable

日期：2026-09-28

## 为什么 MemTable 用跳表

1. 插入只需"抛硬币定层数 + 改指针"，无旋转，实现简单；
2. 天然有序，flush 成 SST 时按 key 升序倒出即可；
3. LevelDB 选它的关键原因：并发友好——读只需原子读指针，
   平衡树的旋转在并发下代价大。

## 设计决策

- **升层概率 1/4、上限 16 层**：期望每层元素数 ÷4，16 层足够覆盖 4^16；
- **删除 = 写墓碑**：旧版本可能还在磁盘 SST 里，内存必须留下"已删"证据，
  真正的物理删除推迟到 compaction（阶段 3）；
- **覆盖 = 原地更新**：MemTable 内最后一次写生效；
- **ApproximateSize 近似记账**：判断何时 flush 用，精确记账得不偿失
  （LevelDB 同样只记近似值）。

## 测试方法：对拍（differential testing）

同一个随机操作序列（40% 插入 / 30% 覆盖 / 20% 删除 / 10% 查询，共 10 万次）
同时灌进跳表和 std::map，任何时刻查询结果必须一致，遍历必须严格升序。
这是验证复杂数据结构正确性的标准手法，比手写 case 覆盖率高一个量级。

## 实测数据

```
TestRandomAgainstMap: 100000 ops, 39218 live keys —— 全部一致 ✓
TestPerf: 1,000,000 puts (64B value) in 0.327s = 3.06M puts/s, ~213MB
```

内存放大观察：100 万条 (key≈9B + value=64B) 实际 ~213MB ≈ 每条 213B，
原始数据 73B——跳表节点指针（平均 ~1.33 个 8B 指针/条 × 层数期望）
+ string 头部 + 对齐的固有开销。这正是后面 SST 用紧凑块编码压缩的意义。
