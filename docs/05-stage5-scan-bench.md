# 阶段 5：scan、压测与封版

日期：2026-09-28

## Scan（范围扫描）

与 compaction 共用同一套归并框架：数据源（MemTable → L0 新→旧 → L1）
各自在 [begin,end) 内顺序取数 → k 路归并 → 最新版本获胜 → 墓碑丢弃。
"点查、归并、扫描"三种操作共享同一套版本规则——这是 LSM 架构优雅的地方。

测试：30000 次随机写后做 500 次随机范围查询与 oracle 全量比对，
覆盖"数据分布在 MemTable+L0+L1 各处"的真实状态。

## 基准数据（WSL2 Ubuntu，10 万次/场景）

| 场景 | 吞吐 | 说明 |
|---|---|---|
| 顺序 put | 18,898 ops/s | 含 flush + compaction 的完整写路径 |
| 随机 put | 9,292 ops/s | 随机 key 覆盖，MemTable 命中率低 |
| 命中 get | 47,431 ops/s | 可能穿透 MemTable→L0→L1 多层 |
| 未命中 get（布隆） | **7,870,321 ops/s** | 布隆直接排除，零磁盘 IO |
| scan | 30 次/s | 每次约 400 行 |
| put（fsync WAL） | 2,051 ops/s | 持久性的价格：约为普通写的 1/9 |

### 数据背后的三个结论（复试可讲）

1. **布隆是 LSM 读性能的第一功臣**：不存在 key 的查询比存在 key 快两个
   数量级——LSM 读放大问题的主缓解手段之一；
2. **顺序写优势**：flush 把内存有序数据一次性顺序写盘，这是 LSM 相比
   B+ 树随机写的立身之本（对比：B+ 树单条插入要随机写多个页）；
3. **持久性不是免费的**：fsync 把吞吐打掉一个数量级，所以工业引擎都
   提供 sync 参数让业务按需选择（RocksDB 的 WriteOptions.sync 同理）。

## 遗留（诚实边界）

- 没有 block cache（每次点查真实 pread）——LevelDB 用 LRU 缓存块；
- compaction 在写线程同步执行，会卡住写入（工业实现用后台线程）；
- 单文件全量归并的 L1，写放大偏大（leveled compaction 更优）；
- 无 MANIFEST，文件集合靠目录扫描 + 文件名约定恢复。
