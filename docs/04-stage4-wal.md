# 阶段 4：WAL 与崩溃恢复

日期：2026-09-28

## 机制回顾（实现在阶段 2 已埋好，本阶段用崩溃测试证明）

- **写前日志**：Put/Delete 先写 WAL 再动 MemTable——"先把要做的事记下来，
  再做"；
- **重放**：Open 时顺序读 WAL 灌回 MemTable；半条记录（尾部）直接截断——
  一条记录要么完整要么不存在（write 原子性到记录边界由"先缓冲再单次
  write"保证，掉电撕页时靠 footer/长度校验兜底，工业实现更严格）；
- **flush 时截断 WAL**：MemTable 数据进了 SST（已 fsync），日志使命完成；
- **测试配置要点**：把 memtable_limit 调到 1GB——保证崩溃时数据
  100% 留在 MemTable+WAL 里，没有 SST 兜底，测试才严格。

## 两个层级的持久性（必须分开讲）

| 故障 | 需要什么 | 本项目 |
|---|---|---|
| 进程崩溃（kill -9） | write 到内核页缓存即可 | ✅ 实测通过 |
| 掉电 / 内核崩溃 | fsync 落盘 | opts.sync_wal 开关（代价：每次写一次同步 IO） |

## 测试设计

1. fork 子进程写入 100 条 + 1 条墓碑，然后 `pause()` 挂起；
2. 父进程 `kill -9`（真·运行中崩溃，析构/清理全部跳过）；
3. 重开引擎：100 条全在、墓碑生效、崩溃后还能继续写；
4. 再开一次：两代数据共存。

教训：第一版子进程写完自己退出了，kill 没赶上——"模拟崩溃"测试必须
确认崩溃真的发生（CHECK WIFSIGNALED）。
